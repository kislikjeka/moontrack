# MoonTrack — Domain Context

Glossary of the ubiquitous language. Terms here are canonical; code and docs should use them consistently. This file is a glossary, not a spec.

## Product north star

**The product optimizes for accurate final tax-lot cost basis and realized/unrealized PnL, not for real-time portfolio fidelity.** In-flight / mid-bridge state and sync freshness are explicitly low-priority; **completeness** (never drop a transaction, never fabricate or reverse a disposal) is what matters. When a trade-off pits timeliness against accounting correctness, correctness wins. This north star adjudicates the sync design: conservative bridge stitching, hold-don't-reverse, and "absent while in transit" all follow from it.

## Sync domain

- **Sync provider** — an external API that supplies decoded on-chain transaction history for a wallet address. MoonTrack has exactly one active sync provider at a time. (Current: migrating Zerion → **Noves Translate API**.)
- **Decoded transaction** — a single on-chain transaction after the sync provider has classified it into an operation type and extracted its token movements. Represented by `sync.DecodedTransaction`. Provider-neutral: the sync platform layer must not name a vendor.
- **Transfer** — a single token (or native-coin) movement within a decoded transaction, with a direction (**in** / **out**) relative to the wallet. Represented by `sync.DecodedTransfer`.
- **Operation type** — the high-level category the provider assigns a transaction (trade, deposit, withdraw, claim, receive, send, execute, …). Mapped to a ledger transaction type by the **Classifier**.
- **Unclassified transaction** — a provider op type Noves could not classify (~6% empirically). Still carries transfers, so it is **not** dropped: routed through the execute / in-out fallback (in-only → `transfer_in`, out-only → `transfer_out`). A **both-direction** unclassified tx is recorded but the both-direction case is **logged at WARN + tagged** rather than silently booked as a `swap`, because auto-swap-classifying an unknown DeFi shape would realize phantom PnL (same failure class as an unstitched bridge). No bespoke unclassified handling is built up front (YAGNI on a 6% unknown bucket) — the WARN trail is the audit surface, to be **validated against real data during implementation**.
- **External ID** — the provider-neutral idempotency key for a decoded transaction, stored as `transactions.external_id` under `UNIQUE(source, external_id)`. Format: **`chain:txHash`** (lowercased), e.g. `base:0xabc…`. A single on-chain tx hash is not globally unique across chains, so the chain prefix is required. Replaces the Zerion-specific `ZerionID`. `source = "noves"`.
- **Idempotency scope** — **global** per on-chain event: one ledger transaction per `(source, chain:txHash)`, independent of which wallet fetched it. When the same on-chain tx is fetched under two of the user's wallets, the second fetch is a silent duplicate-skip at ledger-record time. This is safe because the only case where two of the user's wallets are both parties is an **internal transfer**, which is deduplicated deterministically (see below). `raw_transactions` remains **wallet-scoped** (`UNIQUE(wallet_id, external_id)`) — each wallet keeps its own raw copy and can replay independently; only the *ledger* layer is globally idempotent.
- **Internal transfer ownership** — when two of the user's own wallets are both parties to a transfer, it is recorded **once** as an `internal_transfer` ledger transaction, deterministically owned by the **outgoing (source) side**. The incoming side is skipped by design (not by key collision). This is the single mechanism that reconciles global idempotency with wallet-scoped raws.
- **Wipe (replay)** — `wipe_wallet_ledger(wallet_id)` re-pends a wallet's raws and deletes its ledger rows for replay. Must be **internal-transfer-aware**: wiping *either* participating wallet re-pends the shared `internal_transfer` and both wallets' referencing raws, so ownership is never left dangling. Wipe scope is "any raw_transaction of this wallet references this ledger tx," not `transactions.wallet_id` alone.
- **Bridge leg** — one side of a cross-chain bridge, decoded by the provider as op type `sendToBridge` (source chain, outgoing) or `receiveFromBridge` (destination chain, incoming), action `bridged`. **Empirically (Noves pilot, 2026-07-18): the provider links the two legs in NEITHER direction.** The receive leg carries no reference to source chain/tx; the send leg's recipient is the **bridge contract** (or even the null address), not the destination wallet or chain. The only cross-chain link MoonTrack can ever have is a heuristic (asset + amount + time). See [[bridge-stitching]].
- **Pure-send vs round-trip bridge leg** — `sendToBridge` is overloaded. A **round-trip** leg carries a same-tx `received[]` back to "This wallet" in a *different* asset (bridge-as-swap, e.g. GM LP token out → ETH in same tx) → **not** a cross-chain leg; classify **locally** as swap/execute, never stitch. A **pure-send** leg is everything else → a genuine cross-chain outbound, a stitch candidate. **Calibrated against the real Base/Arbitrum history (issue #33, 2026-07-30):** the discriminator is the *asset*, NOT whether `received[]` is empty. 7 of 9 genuine pure-sends carry a same-tx inbound to "This wallet" — either a dust **refund** of the very asset being sent (observed down to 1e-6 of it) or a small native-coin gas drop — so a rule keyed on "empty `received[]`" would refuse to stitch most real bridges. A same-asset refund is also **netted off** the sent amount before matching, since it never left the wallet and the destination delivers only the net. Symmetric for the receive side.
- **Bridge stitching** — MoonTrack's own **best-effort, deferred, receive-triggered** matching, producing a single **cross-chain `internal_transfer`** that carries the tax lot from source to destination chain (cost basis preserved, no phantom disposal/PnL). **Triggered on the RECEIVE leg**, because only the receive leg carries a usable self-signal: its `to.address` is the user's own wallet ("This wallet"). On a `receiveFromBridge` to the user's own address, look **backward** for a matching **parked pure-send** leg. A pure-send leg with no matching receive is **parked pending**; on a timeout it **falls back** to plain `transfer_out`. Match is **conservative 1:1**: same user, same asset, `received ≤ sent` within a tight fee tolerance (a bridge only takes fees, never adds), destination after source within a time window; on **any** ambiguity (0 or ≥2 candidates) do **not** stitch — prefer a false negative (one recoverable phantom disposal) over a false positive (two real movements destroyed + one fabricated).
- **Cross-chain internal transfer** — an `internal_transfer` whose source and destination legs are on **different chains** (the bridge case). Distinct from the pre-existing same-chain internal transfer between two of the user's wallets. Emitted as **one** ledger transaction carrying both the source-chain CREDIT and destination-chain DEBIT, so the `TaxLotHook`'s existing carry-over path (`taxlot_hook.go:135`) links the destination lot to the consumed source lot and carries weighted-average cost basis across the bridge — **no PnL realized, cost basis preserved**. Requires the `internal_transfer` handler + account resolver to accept `source_chain ≠ dest_chain` (today implicitly same-chain).
- **Tax-lot correctness rule for bridges** — **never realize a disposal that might later be reversed.** A cross-cycle straggler pure-send leg (receive not yet collected) is **held unprocessed** (no ledger tx, no disposal) until it either matches an arriving receive (→ one cross-chain internal_transfer) or ages past the window (→ finalized as plain `transfer_out`, disposal realized only then). **The hold is symmetric (issue #33):** an unmatched *receive* leg is held too, because chains are collected independently (see Wallet chain sync state) so the destination chain is routinely collected before the source. Booking a lone receive immediately as `transfer_in` would mark its raw processed and drop it out of the pending set, leaving the send that arrives next cycle with nothing to match — it would then age out to `transfer_out`, producing `transfer_in` + `transfer_out`: the fabricated disposal and reset cost basis in a different disguise. Past the window an unmatched receive is released as a plain `transfer_in`, so a bridge from a chain outside the wallet chain set never strands the asset. Consequence: a bridged asset is briefly **absent from the portfolio while in transit**. The stitch decision is a **pure function of collected raws** (no matcher side-state), so replay/wipe re-derives the same result deterministically — and the **net matched amount** (gross minus any same-tx refund) is carried from the matcher to the ledger writer rather than re-derived, so the quantity recorded is always the quantity matched on.
- **Genesis balance** — a synthetic transaction the **Reconciler** creates to account for on-chain balance that transaction history alone doesn't explain (positive delta between on-chain position and calculated net flow). Not a real on-chain event.
- **Reconciliation** — Phase 2 of sync: comparing calculated net flows (from decoded transactions) against on-chain positions, and synthesizing genesis balances for unexplained positive deltas.
- **Compatible chain** — a chain the sync adapter *can* handle: it has a chain-slug mapping and verified schema parity with the provider. The upper bound of what the system could sync.
- **Enabled chain** — the subset of Compatible chains MoonTrack actually polls, to bound API cost. Initial Enabled set: **`eth`, `base`, `arbitrum`**. This set is the default **wallet chain set** stamped on a new wallet.
- **Wallet chain set** — the per-wallet, user-editable set of chains that this wallet is synced on. Defaults to the Enabled set at creation. A **hard scope**: sync and reconciliation iterate exactly this set — activity on a chain outside the set is invisible until the user adds it. Must be a subset of Compatible chains. A wallet is still one address across chains (identity is `UNIQUE(user_id, address)`, unchanged); the chain set only says *which chains we bother syncing*, not identity. **Materialized as the rows of `wallet_chain_sync`** — one row per enabled chain.
- **Wallet chain sync state** — per-(wallet, chain) sync bookkeeping: `collect_cursor_at`, `sync_status`, `sync_error`, `last_sync_at`, `sync_phase`. Each chain advances independently, so one chain's provider failure never freezes or corrupts another chain's timeline. Stored in `wallet_chain_sync`. The wallet-level `sync_status` becomes a **derived rollup** over its chain rows (error if any errored; syncing if any syncing; else synced).
- **Collect cursor (high-water mark)** — per-(wallet, chain), collection proceeds **oldest→newest** and the cursor is the `mined_at` of the **contiguously collected** high-water mark: everything at or below it is provably collected. `since` is **inclusive** (`>=`); duplicates on the boundary are absorbed by global idempotency, so the boundary can never *drop* a transaction. Because collection is oldest-first, an interrupted deep sync simply resumes forward from the high-water mark and can never skip old history — this replaces the newest-first model (Zerion-forced), where a crash mid-deep-sync left the oldest (lowest-cost-basis) lots silently unreachable. Whether oldest-first is achieved via a native Noves ascending-sort/range param or by persisting a newest-first window into `raw_transactions` and processing it ascending is an implementation detail (`raw_transactions` is durable and populated before processing, so reordering there is safe). **Noves primitives (verified against docs.noves.fi, 2026-07-19):** `GET /evm/{chain}/txs/{addr}` has a `sort` param (default `desc`) and — the load-bearing primitive — **`startBlock`/`endBlock` and `startTimestamp`/`endTimestamp` range anchors**, so the high-water mark can be enforced by *windowing forward* even if native ascending sort proves unreliable. **NOT doc-confirmed:** the literal `sort=asc` value, that pagination direction follows `sort`, and cursor stability across concurrent inserts. **Plan prerequisite:** one live probe (`?sort=asc&startTimestamp=…`) to confirm ascending behavior before relying on it; the range-anchor + reorder-in-`raw_transactions` path is the fallback and is fully sufficient on its own.
- **Exact decimal conversion** — Noves amounts are decimal strings; conversion to base units (`× 10^decimals` via `big.Rat`/`big.Int`) must be **exact-or-flag**: if the decimal carries more precision than `decimals` (provider rounding / token misreport), do not silently floor — log WARN and flag the transaction, so any reconciliation delta is attributable and never silently seeds a phantom genesis balance.

## Rollout

- **Full replacement**, no dual-provider toggle. De-Zerion the sync vocabulary (`ZerionProcessor` → `Processor`, `ZerionID` → `ExternalID`, `zerion_assets` → chain-scoped asset store, `source="zerion"` → `"noves"`). ~500 Zerion identifiers across ~24 files.
- **Alchemy**: already removed from the sync pipeline per ADR-001 (no Alchemy code remains). The `syncWalletAlchemy` "fallback" in `sync-and-price-flow.md`/the handoff is **stale docs** — nothing to drop. `syncWallet` is already provider-agnostic through the `TransactionDataProvider` port, so the swap is localized to naming + chain fan-out, not control flow. `sync-and-price-flow.md` needs its Zerion/Alchemy sections rewritten.
- **Clean-slate data**: `TRUNCATE` all sync-derived financial data (`transactions`/`entries`/`tax_lots`/`lot_disposals`/`raw_transactions`/`account_balances` for `source IN ('zerion','sync_genesis')`), reset wallet sync state, re-sync from scratch under Noves. **Keep** user accounts + wallet definitions (address, name). No hand-entered data to preserve (zero prod users). Sidesteps all Zerion/Noves dual-representation hazards.
- **Migrations**: keep `000001–000027` as immutable history (the working TimescaleDB hypertable / continuous-aggregate / seed foundation is *unrelated* to sync and must not be rewritten). Add aggressive **forward** migrations `000028+`: de-Zerion rename + truncate; `wallet_chain_sync` table; cross-chain `internal_transfer` columns; internal-transfer-aware `wipe_wallet_ledger`. A full squash-to-baseline is a **separate later cleanup**, only after Noves is proven on real data — never squash schema and change behavior in the same step.
- **`calcLendingUSD` bug fix (in-scope)**: `zerion_processor.go:962` omits `/10^decimals` (inflates lending USD by 10^decimals). Collapse into `money.CalcUSDValue(t.Amount, t.USDPrice, t.Decimals)` at all 5 call sites; add a regression test. Pre-existing but the file is rewritten anyway and it's squarely in the accuracy dimension.

- **Unclassified both-direction** WARN trail validated against real data during rollout. The audit surface exists in two places, both queryable after a real sync: the WARN log line `unclassified transaction with both inflow and outflow recorded for review` (carries `tx_hash`, `chain_id`, `external_id`, `protocol`, `provider_type`, `tx_type`), and the durable `raw_data->>'unclassified_review'` tag on the recorded ledger transaction. Validate by measuring the flagged bucket against a real wallet's history — `{service="backend", component="tx_builder", level="WARN"}` in Loki for the live trail, or for the accumulated set:

```sql
SELECT raw_data->>'unclassified_provider_type' AS provider_type,
       raw_data->>'protocol' AS protocol, type, count(*)
FROM transactions
WHERE raw_data->>'unclassified_review' = 'true'
GROUP BY 1, 2, 3 ORDER BY 4 DESC;
```

Two populations land in this bucket and need opposite responses, which `provider_type` separates: `unclassified`/`unverifiedContract` means Noves itself could not decode the shape — if a protocol hint recurs there, build bespoke handling for it. Any *other* value means Noves returned a type the adapter has no mapping for — that is not an unknown shape, it is an out-of-date mapping table, and the fix is to map it. Until either is done, the bucket stays recorded with the phantom-PnL risk attached rather than hidden.
