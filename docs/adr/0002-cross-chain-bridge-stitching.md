# Cross-chain bridge stitching (сшивание мостовых переводов)

## Контекст

При миграции sync-провайдера Zerion → Noves Translate встал вопрос кросс-чейн мостов (bridge): пользователь переводит собственные средства с одной сети на другую (например Base → Arbitrum). Noves декодирует **обе стороны моста как две независимые транзакции в двух сетях** (`sendToBridge` на источнике, `receiveFromBridge` на назначении, с разницей в минуты-часы).

**Эмпирически установлено (живой пилот Noves, 2026-07-18/19):** провайдер **не связывает две стороны ни в одном направлении**. Сторона-получатель не несёт ссылки на исходную сеть/tx-hash; у стороны-отправителя `to.address` — это **адрес мост-контракта** (или даже нулевой адрес `0x000…000`), а не кошелёк/сеть назначения. Единственная связь, которую MoonTrack может построить, — эвристическая (актив + сумма + время).

Продуктовый north star — **точный итоговый cost basis и PnL**, а не real-time-точность портфеля. Если оставить две стороны несшитыми, `transfer_out` на источнике становится **disposal** (реализуется фантомный PnL, списывается лот по FIFO), а `transfer_in` на назначении создаёт **новый лот по рыночной цене** (cost basis сбрасывается). Перемещение собственных средств — экономически нейтральное событие; несшивание **портит именно ту метрику, ради которой делается миграция**.

## Решение

Сшивать стороны моста в **одну** кросс-чейн `internal_transfer`-транзакцию, чтобы существующий механизм `TaxLotHook` (carry-over cost basis, `LinkedSourceLotID`, `DisposalType=InternalTransfer` → PnL не реализуется) перенёс лот через мост с сохранением базы стоимости.

Ключевые свойства матчинга:

- **Триггер на стороне-получателе**, а не отправителе. Только `receiveFromBridge` несёт полезный self-сигнал: его `to.address` — собственный кошелёк пользователя («This wallet»). Обнаружив входящий bridge-перевод на свой адрес, ищем **назад** припаркованную `sendToBridge`-сторону.
- **Только «чистые» отправки** — кандидаты. `sendToBridge` перегружен: если в той же tx есть `received[]` обратно на «This wallet» в другом активе (мост-как-swap, напр. GM LP-токен → ETH), это **не** кросс-чейн-нога — классифицируется локально как swap/execute.
- **Консервативный 1:1.** Совпадение только при: тот же пользователь, тот же актив, `received ≤ sent` в узком допуске на комиссию моста (мост только удерживает, никогда не добавляет), назначение позже источника в пределах временного окна. При **любой** неоднозначности (0 или ≥2 кандидатов) — **не** сшивать.
- **Hold-don't-reverse.** Cross-cycle-«отставшая» чистая отправка (получатель ещё не собран) **держится необработанной** (нет ledger-tx, нет disposal) до совпадения либо устаревания по окну (→ финализируется как обычный `transfer_out`). Никогда не реализуем disposal, который потом придётся откатывать.
- Решение о сшивании — **чистая функция от собранных raw-транзакций** (без побочного состояния матчера), поэтому replay/wipe детерминированно воспроизводит результат.

## Рассмотренные альтернативы

- **Триггер на отправителе** («пометить исходящую как ожидающую входящую») — отклонён: сторона-отправитель эмпирически не содержит адреса/сети назначения.
- **Жадный матчинг** (ближайший по времени/сумме) — отклонён: ложное сшивание уничтожает **две** реальные транзакции и создаёт одну фантомную; для трекера cost basis это худший класс ошибки. Предпочитаем ложно-отрицательные (одна восстановимая фантомная disposal) ложно-положительным.
- **Process-then-reverse** для отставших ног — отклонён: кратковременно показывает фантомный PnL и требует отката реализованной disposal.
- **Не сшивать вовсе** — отклонён: ломает итоговый cost basis/PnL, то есть основную цель.

## Последствия

- `internal_transfer`-хендлер и account-resolver должны принимать `source_chain ≠ dest_chain` (ранее неявно одна сеть).
- Пока актив «в пути» через мост (отправка собрана, получение — нет), он **временно отсутствует** в портфеле. Это принято осознанно (north star — не real-time-точность).
- `wipe_wallet_ledger` должен быть **internal-transfer-aware** (см. `CONTEXT.md`): wipe любого из участвующих кошельков перепроводит общую `internal_transfer`.
- Матчинг нужно валидировать на реальной истории Base-кошелька (калибровка допуска комиссии, разделение pure-send / round-trip) до релиза.
