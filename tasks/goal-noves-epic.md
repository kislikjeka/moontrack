# GOAL: добить эпик #23 (Noves migration) — тикеты #30 → #31 → #32 → #33 + финальная приёмка

## Цель

Закрыть оставшиеся тикеты эпика #23 (миграция sync с Zerion на Noves) **строго по одному, последовательно**, и затем доказать на реальных данных, что изначальная цель эпика достигнута: транзакции реального кошелька парсятся корректно, а итоговая себестоимость (cost basis) и PnL считаются правильно.

Изначальная цель эпика (#23), с которой сверяется финальная приёмка:

> Продукт существует ради **точной итоговой налоговой себестоимости и реализованного/нереализованного PnL**. Zerion плохо размечал протоколы, схлопывал непонятые операции в generic in/out и терял транзакции — это напрямую портило цифры. Noves заменяет Zerion **полностью** (не аддитивный адаптер). Каждое пограничное решение разрешается в пользу **корректности учёта и полноты, а не своевременности**.

## Правила на каждый тикет

1. Один агент = один тикет. Вызов: `/implement <номер>`. Ничего сверх скоупа тикета.
2. Скилл `/implement` уже включает: TDD на согласованных швах, регулярный typecheck, полный прогон тестов в конце, `/code-review` и коммит. Не дублировать это вручную.
3. Ветка `feat/mt-sync-<краткое-имя>` → после зелёных тестов и код-ревью `git merge --no-ff` в `main` с сообщением `Merge #NN: <summary>` → `git push origin main`. Это конвенция #26–#29.
4. **Перед мержем обязательно**: `go build ./...`, `go vet ./...`, полный `go test ./... -short` — зелёные **на смерженном main**, не только на ветке.
5. Находки код-ревью по оси Spec, указывающие на реальный баг корректности, **чинятся до мержа** (как в #29, где ревью нашло разрыв непрерывности курсора между страницами).
6. Если тикет содержит «Plan prerequisite» (у #33 — калибровка fee tolerance и pure-send/round-trip на реальной истории Base) — это часть тикета, выполнить внутри него.
7. Правила Noves API из `docs/agents/noves-api-capture.md` соблюдать строго: ключ из `.env`, **никогда не печатать**, ≤12 запросов за сессию, переиспользовать фикстуры вместо новых запросов.

## Финальная приёмка (после всех четырёх тикетов)

Запустить **финальных апруверов** и убедиться, что цель эпика реально достигнута.

### A. Сверка со спекой эпика
Прогнать `/code-review` по всему диапазону эпика (`git diff` от точки старта миграции до `HEAD`) против тела #23 — **включая список из 32 user stories**. Явно отчитаться по каждой: выполнена / не выполнена / выполнена частично. Отдельно проверить, что не осталось:
- следов Zerion в sync-слое (вендорная лексика де-вендорена — stories 27–28);
- нетронутыми остались price pipeline (story 31) и ledger core / tax-lot hook / module handlers, кроме cross-chain internal transfer (story 32).

### B. Проверка на реальных данных (главное)
Адрес и креды лежат в `.env`: `PROD_ADDRESS` / `RESYNC_WALLET_ADDRESS`, `RESYNC_EMAIL`, `RESYNC_PASSWORD`. **Секреты не печатать и не коммитить.**

1. Поднять локальный стек: `just dev` (бэкенд в Docker, фронт на Vite :5173).
2. Прогнать полный sync реального кошелька по включённым цепям (eth / base / arbitrum).
3. Убедиться, что **все транзакции распарсились как надо**:
   - нет транзакций, потерянных на сборе (курсор дошёл до конца, `sync_status` = synced по всем цепям, `sync_error` пуст);
   - классификация: swap = swap, lending с реальным активом **и** receipt-токеном, LP с NFT position id — не схлопнуто в generic transfer;
   - разложить по типам и глазами сверить нетривиальные случаи с эксплорером/Noves-ответом;
   - `unclassified` both-direction — записаны, помечены и WARN-логированы, **не** проведены как swap (#30);
   - bridge-легы сшиты в один cross-chain `internal_transfer`, себестоимость перенесена, PnL **не** реализован (#33);
   - двойного учёта нет: один on-chain tx под двумя кошельками = одна ledger-транзакция (#31).
4. Проверить бухгалтерию: каждая транзакция сбалансирована (`SUM(debit) = SUM(credit)`), реконсиляция балансов по цепям сходится, необъяснённые остатки ушли в genesis balance, а не потерялись.
5. Проверить логи через Loki MCP (`{service="backend", level="ERROR"}`, компоненты `sync`, `noves`, `ledger`, `taxlot_hook`) — разобрать каждую ошибку и WARN-хвост.
6. UI-проверка через Playwright MCP (скилл `verify-ui`): залогиниться, открыть портфель / список транзакций / лоты и убедиться, что данные отображаются и не пустые/не битые. Авторизация JWT — по схеме из `verify-ui`.
7. Прогнать интеграционные тесты с `TESTCONTAINERS_RYUK_DISABLED=true` (Colima не даёт reaper смонтировать docker.sock).

### C. Что считается провалом приёмки
Любое из: потерянная транзакция; неверная классификация, меняющая cost basis; фантомный PnL на самобридже или internal transfer; двойной учёт; несбалансированная ledger-транзакция; необъяснённая дельта реконсиляции.
